# Partitioning Tables Across DB Servers

## The Idea

What if we do the partitioning in a way that:

- One DB server has the user-related tables.
- Another is the Order DB server, with the order-related tables.
- Another is the Product DB server, having all the product-related tables.

## Why It Helps

- In a sale, the window shoppers increase by 10X.
- But the number of people ordering is less than the number of people who are just scanning. They buy less.
- So we can scale the Product/catalogue DB server.

## Summary

- This is similar to microservice architecture.
- This is also partitioning: we are partitioning the tables into different DB servers, depending on the application logic.

> 💡 **Added explanation:** this is often called functional partitioning. The data is split by feature (users, orders, products), not by rows.

## Partitioning vs Sharding

- None of these are sharding. These are just partitioning.
- In sharding, things go one level up.
- Sharding is a kind of partitioning where the data of the same table is distributed among multiple database servers.
- So for each table, let's say in one DB server I am storing the range 1-100, and in another we are storing 101-200.

### Example

- In the orders table, we also store the `countryId`, to know in which country the order was placed.
- That way, we can do hash-based partitioning on `countryId`.
- A group of orders for, let's say, Asia goes in one DB server.
- There is very little chance that people from the USA place an order in India. So we can reduce the cross-continent calls and all.
- All of Asia will be hitting the Asia DB server only.

> 💡 **Added explanation:** grouping orders by region like this is often called geo-based sharding.
