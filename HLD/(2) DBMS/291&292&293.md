## ACID

- **Atomicity**
  - It guarantees that the DB executes a transaction completely, or rolls back any partial completions
  - It ensures no partial updates
  - A good way to implement this is **log-based recovery**
- **Consistency**
  - It is a property with which our data moves from a valid state to another valid state
  - DBs having high consistency will never leave your data in an inconsistent state
- **Isolation**
  - It's a transaction property that defines how concurrent transactions should be handled
  - Let's say two concurrent users are trying to book a ticket for anything, there isolation comes into play
  - Issues with concurrency are:
    - **Dirty reads**: it occurs when a transaction retrieves a row that has been updated by another transaction that is not yet committed
    - **Non-repeatable reads**: it occurs when a transaction retrieves a row twice and the row is updated by another transaction that is committed in between
  - **Isolation levels**
    - **Serializable**: this is the highest isolation level, with lock-based concurrency control. Serializability requires read and write locks to be released at the end of the transaction. It will take more system resources
- **Durability**
  - It's a guarantee provided by the DB such that if a transaction is committed, all the changes done by it will persist even if there is a DB crash

If any DB follows all these properties, then we call that DB **ACID compliant**, and it favours transactions in the database
