## Which database to choose?

- No one database will be able to solve the problem. There is a good variety of databases to solve problems

### Criteria

- Based on the team's knowledge, we can also prioritize a particular DB
- There is good knowledge of **RDBMS**, so you can prefer that
- If we need a graph-like structure, like social media applications, here you go for some graph-like databases. Databases like **Neo4j**, **InfiniteGraph**, etc. can be opted
- If you have unstructured data, this is probably schemaless, and you can store it in the form of documents. Then **document-based databases** are very useful
- If you want to store **key-value pairs**, let's say user ID <-> connection data, e.g. **Redis**, **DynamoDB** are a good choice
- Sometimes geolocation data is the use case. Then **geospatial** DBs like **Redis** geospatial, **Firebase** geospatial, etc. are useful
- If you have relational data which is also structured, then **RDBMS** is good
- If you have transactional data, then **RDBMS** is also good
- Bookings: in any case, there also you can use **RDBMS**. It is good, concurrency as well
- **File storage**: we have **Blob storage** (binary large object), like images, videos or any files like AWS S3

## Transaction

- It is a logical unit of work which comprises multiple steps in itself. In a transaction, all the sequence of steps should either complete successfully or none of them should complete. There cannot be a partial completion stage

- In DB terms, if all the steps of a transaction have completed, we call it a **commit**. If some of them completed and a few did not, then the DB rolls back all the operations, and this situation is called **ABORT**

- Not only **RDBMS** gives transactions, but even **MongoDB** gives transactions. But **RDBMS** has end-to-end support for transactions

```sql
START TRANSACTION;
-- Code Steps
COMMIT;
```
